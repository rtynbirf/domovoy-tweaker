# Техническая спецификация ДОМОВОЙ

Версия документа: 0.3.0 · Статус: активный прототип · Обновлён: 2026-11-02

---

## 1. Цель и суть

### 1.1. Суть

ДОМОВОЙ — инструмент управления настройками Windows, в котором каждый твик
является **управляемым состоянием**, а не разовым действием. «Управляемое состояние»
означает: зафиксировано до изменения, записано после, проверяемо в любой момент,
восстановимо по отдельности.

### 1.2. Проблема

Существующие инструменты (включая всех «учителей» — см. `comparison.md`) применяют
настройки как событие. Через месяц пользователь не может ответить на вопросы:
«что именно я менял?», «что из этого пережило обновление Windows?», «как отменить
только одну функцию, не трогая остальные?».

### 1.3. Решение

Четыре контура: Журнал (Ledger), Машина времени (undo по-функционально),
Дозор (детекция дрейфа), Проверка эффекта (верификация пробами).
Подробно — `architecture.md`.

### 1.4. Не-цели

- Не антивирус и не «оптимизатор-ускоритель» с пустыми обещаниями.
- Не система резервного копирования всего ПК (только то, что трогаем сами).
- Не инструмент удалённого/корпоративного принуждения (локальная машина, локальный админ).
- Не замена групповым политикам — наоборот, экспорт в них запланирован (v0.7).

## 2. Термины

| Термин | Значение |
|---|---|
| **Функция (Feature)** | Единица твика с манифестом: id, операции, пробы, откат |
| **Манифест** | JSON-файл декларативного описания функции (`schema/features.schema.json`) |
| **Операция (op)** | Атомарное действие: `registry.set`, `registry.delete`, `service.startup`, `service.stop`, `appx.remove`, `file.attribute` |
| **Проба (probe/verify)** | Проверка фактического состояния, соответствующая операции |
| **Снимок (snapshot)** | Значения ДО применения, восстановимые при undo |
| **Журнал (Ledger)** | Append-only JSONL-файл всех событий изменения состояния |
| **Дрейф (drift)** | Расхождение фактического состояния с зафиксированным ожидаемым |
| **Dry-run** | Показ плана изменений без применения (режим по умолчанию) |

## 3. Окружение и требования

- ОС: Windows 10 (2004+) и Windows 11, x64.
- PowerShell: 5.1 (Desktop) и 7+ (Core). Оба обязательны к поддержке.
- Права: чтение каталога функций — любые; `-Apply` и undo — elevated-сессия
  (проверяется `Test-DomovoyAdmin`, а не «повезёт/не повезёт»).
- Кодировки: `.ps1/.psm1/.psd1` — ASCII-only в коде (совместимость PS 5.1);
  JSON — UTF-8; журнал — UTF-8 JSONL.
- Хранилище: `%ProgramData%\Domovoy\`, переопределяется переменной `DOMOVOY_STORE`
  (используется тестами и CI).

## 4. Архитектура верхнего уровня

CLI-first. GUI — отдельный слой не раньше v0.7 (см. `roadmap.md`).
Модуль `Domovoy` не содержит сетевых вызовов вообще — это инвариант I4 (§7).

## 5. Модель данных

### 5.1. Манифест функции

JSON по схеме `schema/features.schema.json`. Обязательные поля:

```text
id          — 'category.object.action', строчные латинские/цифры/точки/дефисы
title       — человекочитаемое название
version     — SemVer версии самой функции
category    — privacy | services | apps | ui | network | maintenance | drivers | security | core
risk        — low | medium | high
description — что делает, одним абзацем
ops[]       — операции применения
undo        — { "mode": "snapshot" } (обязательно; другие режимы — после v0.3)
verify[]    — пробы эффекта (обязательно ≥1)
references[]— ссылки на документацию Microsoft (обязательно, https)
```

Типы операций (v0.3):

| op | поля | обратная операция из снимка |
|---|---|---|
| `registry.set` | `path, name, value, valueType` | восстановление `previousValue`/`previousType` или удаление значения, если его не было; если ключ создан самим твиком (`pathExisted = false`) — удаляется и пустая цепочка созданных ключей |
| `registry.delete` | `path, name` | то же: восстановление прежнего значения с типом или ничего, если значения не было |
| `service.startup` | `name, startupType` | восстановление прежнего типа запуска |
| `service.stop` | `name` | запуск службы, если до твика она была `Running`; остановка, если была `Stopped` |
| `appx.remove` | `name, removeProvisioned?` | пере-регистрация пакета из места установки (без сети); provisioning не восстанавливается — честный отчёт |
| `file.attribute` | `path, attributes, allowMissing?` | точный прежний набор атрибутов (бит `Directory` сохраняется) |

Типы проб (v0.3): `registry.set` (равенство значения), `registry.absent` (значение
отсутствует), `service.startup` (тип запуска), `service.status` (фактический статус),
`appx.absent` (пакет отсутствует), `file.attributes` (все перечисленные атрибуты установлены).

Планируемые типы операций: `scheduler.task`, `service.config`,
`profile.export` (см. `roadmap.md`).
**Инвариант расширения:** новый op-тип принимается только вместе с проекциями
probe / snapshot / undo (§6.4).

### 5.2. Снимок

Список записей `{ op, path|name, previousValue, previousType }` — по одной на каждую
операцию манифеста, собранную перед применением. Дополнительно: `registry.set` несёт
`pathExisted` (существовал ли ключ до твика), `appx.remove` — `packageFullName`,
`installLocation`, `provisionedPackageName`, `file.attribute` — `previousAttributes`,
`scheduler.task` — `previousState`.

### 5.3. Профиль

JSON по схеме `schema/profiles.schema.json`: `id`, `title`, `maxRisk`
(low | medium | high), `description`, `features[]` (id функций). Профиль — данные,
не код: Invoke-DomovoyProfile пропускает функции с риском выше потолка и сообщает
об этом честно.

### 5.4. Журнал (Ledger)

Файл `ledger.jsonl`, по событию на строку:

```json
{"schema":1,"event":"feature.apply","tool":"Domovoy","toolVersion":"1.2.0",
 "timestamp":"2026-11-02T12:00:00.0000000+00:00","featureId":"...","featureVersion":"1.0.0",
 "featureSource":"C:\\path\\to\\manifest.json",
 "snapshot":[...],"verification":{"feature":"...","allPass":true,"results":[...]},
 "prevHash":"genesis","hash":"64 hex chars"}
```

С v1.2 каждая новая запись несёт хеш-цепочку (№103, аддитивно — schema
остаётся 1): `hash` — SHA-256 канонической JSON-формы записи (все поля,
кроме `hash` самого; канонический сериализатор с ordinal-сортировкой ключей
и инвариантной культурой — одинаковый на Windows PowerShell 5.1 и 7.x),
`prevHash` — `hash` предыдущей записи или литерал `genesis`. Целостность
проверяет `Test-DomovoyLedgerIntegrity`: записи до v1.2 считаются
`unchained`, журнал целиком до v1.2 — `ChainState = absent` (это честный
ответ, а не ошибка); правка или перестановка записей даёт `broken` с
номером строки.

События: `ledger.init`, `feature.apply`, `feature.undo`, `cleanup.apply`
(очистка temp: фиксирует факт и объём; необратима по дизайну, поэтому — не
манифест и без undo-снапшота, см. §9), `networkreset.apply` (сброс сети:
снапшот снимаемых настроек — статические IP и DNS), `eventlog.cleanup.apply`
(очистка журналов событий: записи до/после), `memorytrim.apply` (тримминг
рабочих множеств: байты до/после, честная пометка), `integritycheck.apply`
(sfc/DISM: инструмент, код выхода, файл с полным выводом), `group.apply`
(v1.3: группа — порядок и счётчики; каждая фича группы дополнительно
пишет свой `feature.apply`), `ledger.migrate` (v1.3: аудит миграции схемы —
откуда/куда, сколько записей, имя бэкапа). Полный список — валидатор
событий `Get-DomovoyLedger`: он же — единый источник правды, фильтрация
по событию работает для каждого элемента списка.

### 5.5. Миграция схемы журнала

Версия схемы записи — поле `schema` (сейчас 1); единый источник правды —
`Get-DomovoyLedgerSchemaVersion`. Инвентаризация — `Get-DomovoyLedgerSchema`
(только чтение): записи без поля `schema` и записи с версией НОВЕЕ
известной считаются отдельными честными категориями; журнал более новой
версии Домового никогда не понижается. Миграция —
`Invoke-DomovoyLedgerMigration`, сухой прогон по умолчанию: `empty` /
`already-current` (Apply — честный no-op, файл не переписывается) /
`future-entries` (на Apply — громкий отказ) / `migration-not-defined`
(правило преобразования не определено в этом релизе — ничего не
меняется). Реальная перезапись — явное, аудируемое исключение из
append-only: только по определённому правилу, только после побайтового
бэкапа (`ledger.backup-*.jsonl`), только когда каждая строка читаема
(битая строка останавливает всё до первого изменённого байта), с
перестройкой хеш-цепочки тем же контрактом, что у писателя, и записью
`ledger.migrate`.

### 5.6. Хранилище

```text
%ProgramData%\Domovoy\
├── ledger.jsonl                 # журнал (append-only)
├── ledger.backup-*.jsonl        # побайтовые бэкапы журнала перед миграцией схемы (№101)
├── snapshots/<featureId>/<ts>.json   # явные снимки (Backup-DomovoySnapshot)
└── backups/                     # экспорты состояния (Backup-DomovoyServiceState)
```

## 6. Алгоритмы

### 6.1. Apply (`Invoke-DomovoyFeature`)

1. Прочитать и провалидировать манифест.
2. Построить план: для каждой операции — текущее значение (реестр) или тип запуска (служба).
3. Нет `-Apply` → вернуть план и завершиться (dry-run по умолчанию).
4. Проверить elevation; без прав — ошибка, ничего не тронуто.
5. Создать точку восстановления (мягко; ограничение ОС — раз в 24 ч).
6. Собрать снимок текущих значений.
7. Выполнить операции по порядку.
8. Прогнать пробы `verify`.
9. Записать событие `feature.apply` в журнал.
10. Любое исключение на шагах 7–8 → частичное применение фиксируется в журнале
    с `verification.allPass = false` и пробрасывается наверх.

### 6.2. Undo (`Undo-DomovoyFeature`)

1. Найти последнее событие `feature.apply` для `featureId` в журнале.
2. Dry-run без `-Apply`: показать снимок, который будет восстановлен.
3. Восстановить каждое значение из снимка (тип включительно; «не было» → удалить).
4. Прогнать пробы; записать событие `feature.undo`.

### 6.3. DriftScan (`Invoke-DomovoyDriftScan`)

1. Из журнала взять последнее событие по каждой функции (`feature.apply` или
   `feature.undo`); функция, последнее событие которой — undo, сейчас не
   применена и не сканируется.
2. Базовая линия — **не манифест, а последний verified-снимок**: пробы,
   записанные в событии `feature.apply` сразу после применения.
3. Прогнать те же пробы сейчас; `drifted = фактическое значение ≠
   verified-значению` (для проб без базовой линии — ожидаемому из манифеста,
   с честной пометкой).
4. `-Since X` ограничивает скан функциями, применёнными после момента X.
5. Отчёт: scanned / drifted / detectedAt; по каждой функции — featureId,
   appliedAt, detectedAt и детали `{probe, target, verified, expected,
   actual, pass}`.
6. (v0.6) opt-in авто-лечение.

### 6.4. Verify (`Test-DomovoyEffect`)

Проба → фактическое значение → строковое сравнение с ожидаемым →
`{probe, target, expected, actual, pass}`. Матрица проб возвращается всегда, честный FAIL — норма.

## 7. Инварианты безопасности

| № | Инвариант |
|---|---|
| I1 | Журнал append-only: события не редактируются и не удаляются |
| I2 | Снимок собирается ДО первой операции; без снимка применение запрещено |
| I3 | Dry-run по умолчанию: применение только при явном `-Apply` |
| I4 | Нулевой сетевой контур в модуле (нет `Invoke-WebRequest`/`WebClient`/`curl` в коде) |
| I5 | Elevation проверяется явно; без прав изменения невозможны |
| I6 | Идемпотентность: повторный apply не меняет результат |
| I7 | Манифест без `undo` или `verify` не загружается вообще |

## 9. Известные ограничения (честно, v0.5)

1. `appx.remove`: undo пере-регистрирует пакет только если файлы пакета ещё на
   диске; если удалены — честный отчёт и подсказка документированного источника
   восстановления (Store/winget). Provisioned-пакеты при undo не
   восстанавливаются.
2. `service.startup` меняет только тип запуска, не останавливая работающую службу;
   для остановки есть отдельный op `service.stop` (с снимком статуса и запуском при undo).
3. Точка восстановления ограничена ОС (раз в 24 ч) — фиксируется в журнале.
4. Единой команды «undo профиля» нет: откат — по-функционально через `Undo-DomovoyFeature`.
5. `file.attribute` только добавляет перечисленные атрибуты (OR); «снять атрибуты
   с чужих файлов» — отдельная функция №47 (v0.6), с журналом прежних атрибутов.
6. Undo `registry.set` удаляет пустую цепочку созданных твиком ключей только
   лист + пустые предки; неопустевшие родительские ключи остаются (честно, безопасно).
7. `scheduler.task`: undo возвращает прежнее состояние задачи; задача, удалённая
   кем-то после твика, заново не создаётся — отчёт честный.
8. `Invoke-DomovoyCleanup` необратима по дизайну (удалённые файлы не
   восстанавливаются): трогает только обычные файлы в temp текущего
   пользователя старше N дней; факт, объём и неудачные файлы — в журнале.
9. Сброс сети (`Invoke-DomovoyNetworkReset`): сам каталог Winsock и LSP-записи
   третьих сторон восстановлению не подлежат — это честно сказано в отчёте;
   undo восстанавливает только снимаемые настройки (статические IP и DNS).
   После сброса обычно требуется перезагрузка.
10. Тримминг памяти (`Invoke-DomovoyMemoryTrim`) — временный эффект: страницы
    возвращаются, как только процессы снова их затребуют; это инструмент
    диагностики, а не «ускоритель».
11. `Invoke-DomovoySystemIntegrityCheck` запускает только сканирующие
    варианты (`sfc /scannow`, `DISM /ScanHealth`); восстановительные операции
    DISM с изменением хранилища компонентов — вне модуля.
12. `Get-DomovoyBitLockerStatus` только отображает состояние; включение/выключение
    шифрования — за рамками модуля. На редакциях без BitLocker-модуля — честная ошибка.

## 10. Версионирование и релизы (MAJOR-политика, с v1.0.0)

- SemVer: MAJOR — ломающие изменения; MINOR — новые функции/op-типы/пробы;
  PATCH — исправления.
- Conventional Commits; CHANGELOG.md ведётся с первого релиза.
- Теги `vX.Y.Z` только на `main`; release notes — по CHANGELOG.

### Обещание совместимости v1.x

Начиная с 1.0.0 **внутри всех версий v1.x** следующие форматы заморожены:
разрешено только добавлять, запрещено менять смысл уже существующего.

**Журнал (Ledger, JSONL):**
- существующие типы событий (`ledger.init`, `feature.apply`, `feature.undo`,
  `cleanup.apply`, `autoheal.cycle`, `privilege.enable/disable`,
  `driverdedup.apply` и другие) и семантика их полей не меняются никогда;
- новые типы событий и новые поля существующих событий добавляются без
  смены MAJOR; читатели обязаны игнорировать неизвестные поля;
- устойчивость к битой строке сохраняется как есть (append-only, I1);
- журнал, написанный любой v1.x, читается всеми последующими v1.y (y ≥ x).

**Манифесты и схема (`schemaVersion = 1`):**
- семантика существующих op-типов и проб (см. docs/ops.md) не меняется:
  `registry.set` всегда означает «задать значение с откатом из снимка» и т.д.;
- новые op-типы, пробы и поля манифеста добавляются как MINOR;
- манифест, валидный в 1.0.0, остаётся валидным во всех v1.x и означает
  то же самое.

**Хранилище (`%ProgramData%\Domovoy\`):**
- расположение и имена файлов (журнал, снимки, verified-базовая линия)
  не переименовываются и не перемещаются внутри v1.x.

**Публичные команды PowerShell:**
- параметры существующих команд не удаляются и не переименовываются;
- новые параметры — только необязательные, со значениями по умолчанию,
  воспроизводящими прежнее поведение.

**Что требует MAJOR (2.0):** удаление/переименование типов событий или
полей, смена семантики op-типа или пробы, подъём `schemaVersion`,
переезд хранилища, удаление публичных команд.

Пометка «запланировано vX.Y» в каталоге — это честное намерение, а не
обещание формата: до реализации новые функции могут меняться свободно,
формат журнала и манифестов — нет.
